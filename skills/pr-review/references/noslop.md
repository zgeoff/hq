# noslop

noslop is the review on every repo `hq noslop` lists, after the agent's own self-review, and `z-stu` keeps the list. No Codex review runs beside it, because two reviewers double the rework without catching more.

- **The review.** `hq review <repo> <pr>` runs noslop there. It posts each finding on the PR as a review comment by `noslop-review[bot]`, holding `<!-- noslop:finding {...} -->` with the finding's 16-hex id, and a summary comment, `### noslop`, that lists every finding and its state. A finding with no line in the diff is an issue comment by the same bot, with the same marker. The `noslop` check passes only when every finding has an answer. It updates only when `hq review` runs again, never when a reply is posted.
- **The answers.** Each answer is a reply in the finding's own thread, whose first line holds only its disposition: `fixed <sha>`, `not-a-defect <reason>`, `deferred <GEO-n>` or `accepted-risk <reason>`. Any explanation goes on the lines after it: noslop ignores an answer with anything after `fixed <sha>` on its first line. An answer to an issue-comment finding is a new issue comment that starts with the finding's id. The agent answers `fixed` and `not-a-defect`. A `fixed <sha>` counts when that commit changes any file of the PR and the next review no longer reports the finding. noslop refuses `deferred` on a line the PR added or changed. Never quote the text `<!-- noslop:` in a reply: hq and noslop take any comment that holds it for noslop's own, so they skip the reply and read its fix as unnamed.
- **A taste finding.** noslop accepts any reasoned `not-a-defect`, so check each one before the merge. When the finding quotes a skill rule, the answer counts only when it quotes the text that shows the rule doesn't apply: the shared rule's own wording, or a line of the repo's project skill that the shared skill lets it hold. Each shared skill says what its project skill may do: code-style and testing let it only add, such as a project verb or a stricter rule, so a project line that relaxes one of their rules is no answer; docs-writing lets the project skill win where the two disagree. Otherwise send it back to the agent to fix.
- **Your part.** For each finding the agent's final report leaves unfixed, apply the reason test in `follow-ups.md` from `SKILL.md`'s reference list, and file the ones that hold as it says; they end with `deferred GEO-<n>` in the thread. Reply `accepted-risk <reason>` only with the owner's answer. What makes his answer count, and how the reply cites it, is in this file's private half: read `skills/pr-review/references/noslop.private.md` in the local hq-private clone (`hq defs` shows where it is) and follow it as part of this skill. Then ask `z-stu` to record it with `hq pr accept-risk <repo> <pr> <finding-id> --source <source> --note '<why>'`: the gate counts an accepted-risk finding as open until that record exists. To get his words, send the finding to `z-triage` as a decision, and hold the merge until they come; or answer another way. A true finding, however small, is a defect: fix it. It is deferred only under the reason test. `not-a-defect <reason>` needs no word of his, but only for a finding that is wrong, or a taste rule that doesn't apply, quoted as a taste finding below requires. Send the agent each finding it left unanswered, as step 3 of `SKILL.md` says. Run `hq review` again after the agent's next FINAL note: it reviews the new commits and checks the answers. noslop gives a PR 1 round when it is a sync, release or docs-only PR or its first review routed light, and 2 rounds otherwise. Round 2 reviews only the commits since round 1, so `hq review` drops `--full` there. Past the cap, `hq review` refuses with `round_cap`. A fix pushed after the last round counts only once a review reads it, so run `hq review <repo> <pr> --fixes-only` before the gate: it checks each fix answered since the last round, runs no lens over the diff, raises no new finding, and is not a round, so the cap does not stop it. It reports each fix as fixed or not fixed. Answer a fix it reports as not fixed by fixing it again. It runs only when, since the last round, a `fixed <sha>` answer names each commit that is not a merge, and each merge is a merge of a commit in the PR's base branch, clean or with conflict resolutions, even if an answer names it; otherwise it refuses with `fixes_only_no_fix`, names those commits, and calls no noslop. Apart from the one `--redesign` round in `SKILL.md`, no round runs past the cap: the owner's limit is 2. Code after the last round that no `fixed` answer names and no round read, a fix spread over several pushed commits among it, does not merge in this PR: the same agent opens a new PR for it at once, under the same issue with "Contributes to", which gets its own first round and needs no new issue, or drops it. A fix stays in this PR. A clean merge of a branch other than the base brings in code no lens has read: have the agent move that code to a new PR, or drop it. In a merge of the base with conflict resolutions, noslop checks each resolution in that `--fixes-only` run, and a later `--fixes-only` run counts the merge only when noslop's summary comment lists it as checked. When noslop judges a resolution not sound, `hq review --fixes-only` refuses with "noslop judged the conflict resolution of a merge not sound": send the agent each finding noslop raised on it, answered like any other finding. A merge of a branch other than the base is still refused. The check needs an earlier review that ran its lenses on a head the branch still holds, or one it maps onto a rebased branch by patch id; it refuses when the rebase changed, dropped or reordered a reviewed commit, or the branch holds a merge; it cannot be given with `--full` or `--redesign`. When the agent's answer to your message says every finding has its answer with no new commit, run `hq review check <repo> <pr>` instead, since `hq` sends no new FINAL for an unchanged head. It always exits 0: its JSON field `conclusion` holds `success` or `failure`, and its text lists the findings still open.
- **An owner override.** When the owner says to merge a PR anyway, in an answer that counts as this file's private half says, ask `z-stu` to record it: z-stu runs `hq pr override <repo> <pr> --source <source> --note '<why>'` and tells you when it is on record. The override passes every open finding at the PR's head, never red CI, and a push needs a new override. `hq pr status <repo> <pr>` shows it. An approval from a session, or your own judgment, is not an override.
- **The gate.** `hq review gate <repo> <pr>` passes on green CI, a completed noslop review of the PR on record, and no open finding at the head (an accepted risk is not open), or the owner's override at that head; it refuses when the head moves while it runs. It does not check that a review read the head, so run `hq review` or `--fixes-only` after each push before you run the gate.
- **A head noslop hasn't read.** Run `hq review <repo> <pr>` first: it checks the late commits, as its own round. Send the PR to `z-stu` under its noslop gap rule only when the round cap stops a new review, and you have read the fixes by hand and found them right.
- **When noslop fails to run.** Hold the merge, and message `z-stu` the error: it can switch noslop off for that repo. A Codex review in its place would merge the PR on a different standard from the rest of the repo.
