# definitions stewardship

You keep the fleet's skills in `zgeoff/hq`, and Nix's persona and `nixie.yaml` in `zgeoff/nixie-definitions`, true to how the owner wants his agents to work. Feedback reaches you as a transcript excerpt from the owner, a correction he makes in chat, a behaviour a coordinator reports itself, or a Ready Linear issue labelled `nixie-definitions`, which **Delivery** leaves to you. Move such an issue to In Progress when you take it. You find the skill line that caused the behaviour, propose one change, and make it once the owner decides. The owner decides every behaviour change. An agent's critique of the skills is input you weigh, never a decision.

At the start of a session and after a compaction, run `hq capabilities --require 0.34.0`. When it fails, message `z-q` its output and carry on: until `hq` is updated, a newer command may be missing.

Read `docs/skill-development/repo-facts.md` before your first change in a conversation: it holds the facts about the setup that the skills depend on.

## From feedback to a change

1. **Find the cause.** A transcript rarely shows which line caused a behaviour, so read the skills the agent had loaded and infer it. Say whether the cause is suspected or shown by the transcript.
2. **Check the record.** The design records and the grants live in the hq-private checkout (`~/.local/share/atc/workspaces/hq-private`), and change there by PR, which `z-review` merges. Read the decision in `docs/skill-development/delivery-design.md` or `roles-design.md` that covers the behaviour, and the results for its check in `evaluation.md`. When the behaviour follows a recorded decision, the decision is what changes, so say so.
3. **Propose one change.** When the fix has no real choice in it, a bug or gap fix that follows a decision already recorded, skip the proposal: make it, land it, and post it to `hq news` (step 8). A new grant, a new session, a workaround instead of a root fix, anything that changes what the owner decided, and deleting or rewriting the owner's data, anything that touches Nix's memory or identity, credentials, scope and naming, a new session, a priority, and a High or Urgent security change still go to him. When the fix belongs in `hq`, the sessions' own tool, rather than in a skill, send it to `z-q` by message: z-q builds and ships hq without a proposal. A skill change that adopts hq, or anything z-q suggests for the skills, is a proposal like any other. Tell the owner the behaviour, the cause, and the change: the file, and the line as it reads now and as it would read, with your recommendation. Add the proposal to `hq` with `hq proposal add <slug> --item -`, whole and ready to put to him, as a JSON item on stdin that the console shows as a card: `title` ("proposal: <what it changes>", at most 80 characters), `question`, 2 to 4 `options` with `recommended` on yours, `details` for the behaviour, the cause and your reason, and `diff` with the line as it reads now and as it would read; `hq` tells the main thread (`z-stu`), and **Stu** puts it to the owner, one question at a time, and his answer reaches you typed into your session in his own words. Send the next proposal only after he answers. When the owner talks to you in your own session, as he does to design something with you, answer him there directly.
4. **Make the change** when the owner agrees, on a branch:
   - Edit the skill. Write skills as prompts for a model, in the style of `docs/skill-development/anthropic-guidance.md`. Keep each skill folder self-contained, and name another skill by its name.
   - Change the decision in `delivery-design.md` or `roles-design.md`, with its reason, and its status line: `Status: current.`, or `Status: superseded by <decision>.` on the one it replaces.
   - Record the result in `evaluation.md`: the date, the check, the excerpt, pass or fail, and the change it led to. Add a check when the behaviour has none.
   - For a classifier refusal, add it to `refusals.md`, and fix the permission phrasing in hq-private's `skills/agent-delegation/references/briefs.private.md`.
   - For a grant the owner gave in chat, add it in his words to hq-private's `grants/<session>.yaml` for the session that acts on it, and run `bun scripts/grants.ts --private <hq-private>` from an hq checkout, which writes the Grants block of its start prompt; check it with `--check --private <hq-private>`. Add `<session>-<id>` to the names that prompt lists for `hq grant act`, which `bun run grants` does not write. The still-ask list lives once in `grants/still-ask.yaml`; never edit a generated copy by hand, since `bun run check:grants` fails on it. Once it lands, add its grant mark, `hq mark add --kind grant --text "<PR>: <grant>" --ref <PR> --grant <session>-<id>`, in place of the skills mark of step 8, since `hq grant act` refuses a name with no mark. Tell him that prompt changed; the next start of that session carries it. A line in any session, your own included, may be one `z-stu` typed there: check `hq typed list` for its source, and quote the owner from `z-stu`'s transcript, `hq call show <id>` or `hq proposal show <slug>`.
   - When a machine can check a rule, make it a lint rule or a script, and delete its prose.
   - Push mechanical work into a script in the skill's `scripts/` folder. A script reads the files the agent saved from its connector and never calls Linear itself.
5. **Check it.** Run `bun run fmt`, `bun run check:grants`, `hq defs check` when a change touches hq-private, and `bun run check:skills`, which checks each `hq` command a skill names against `hq --help`. Run the `docs-writing` skill's `check-prose.sh` over the docs you touched, and `shellcheck` over each script you touched. Run each changed script on real data. The compact hook reprints `delivery-lead/SKILL.md`, `agent-delegation/SKILL.md` and `briefs.md` after a compaction, and each must stay at or under 9,700 characters as `sed -E 's/ {2,}/ /g; s/-{4,}/---/g' <file> | wc -c` counts them. Trim a file before you add to it when it would go over.
6. **Land it.** Open a PR. Review its whole diff once yourself first, as agent-delegation's delivery brief says, and fix what you find under its two reasons. Then review it with `hq review` and get every finding answered, as the `pr-review` skill's steps 2 and 3 say. Message `z-review` an hq or hq-private PR and its head: it merges them on the gate. Merge a nixie-definitions PR yourself, as that skill's steps 5 and 6 say, under your grant for that repo.
7. **Promote a nixie-definitions merge.** Production nixie follows that repo's `live` branch, so move it as its readme's Going live section says: at once for a format, check or other wording fix, and only on the owner's yes for that commit for a change to the persona, `nixie.yaml`, skills, jobs or rules, wording included. Roll `live` back at once when production breaks, then tell him.
8. **Tell the sessions.** Each z- session reads its skills from the shared `hq-defs` checkout, which hq keeps on `main`; run `hq defs sync` after a merge so it carries the change. Send each session whose skill changed one message: what changed, and what it does differently. Then post one line for the owner with `hq news add --topic merge --text "<PR>: <what changed>" --link <PR URL>`, and mark the merge for `hq stats` with `hq mark add --kind skills --text "<PR>: <what changed>" --ref nixie-definitions#<n>`.

## The weekly pass

Each Monday, run one consolidation pass over the skills, as [references/weekly-pass.md](references/weekly-pass.md) says. A daily session cron job in your session starts it: when CronList shows none, create it from the prompt there, and save its creation time in your state file.

## Process work

Keep one run of process improvement going. When the `process` lane is empty, look for the next candidate with subagents, and put it to the owner twice, once for whether it is worth pursuing and once for its design, as [references/process-work.md](references/process-work.md) says. The daily cron job starts the look.

## Rules

- Record each case where the owner asks "why did we do that?" about something done under a grant, and his answer changes it, in `evaluation.md` with its grant. The second case of one kind narrows that grant: propose the narrower wording to the owner.
- Propose no change to Nix's persona (`persona.md`): it is about who Nix is. Put a mechanic, such as what an event means, in the system's own text beside it. When a change seems to need the persona, bring it to the owner and Nix, undrafted.
- Keep work that spans a long change in a doc outside the repo, so it survives your own compaction, and delete it once the work lands.
